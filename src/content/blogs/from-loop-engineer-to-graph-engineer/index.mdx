最近看到 B 站视频[《告别 Loop Engineering：Graph Engineering 到底是什么？》](https://www.bilibili.com/video/BV1tegr64EWz/)。视频用一个每天自动生成晨报的 Agent，解释怎样把单一循环拆成多个 Agent 协作的图。

它的[英文原视频](https://www.youtube.com/watch?v=Joqh7Tui9B8)来自 Chase AI，标题是 _Move Over Loop Engineering, Graph Engineering Is Now Here_。

“Graph Engineering”听起来很像又一个追逐流量的新术语，但它指向的问题是真实的：当一个 Agent 要同时研究多个来源、保存大量上下文、自己审查自己，还要从头重试时，单循环会逐渐失去可控性。

不过，Graph Engineering 也很容易被误解成“多开几个 Agent”。如果只是把一个复杂提示词复制成五份，再让五个模型同时消耗 token，我们得到的不是工程化，而是分布式混乱。

真正的变化不是 Agent 数量增加，而是控制结构改变：

```text
Loop Engineer
设计一个执行者如何持续行动、观察和修正

Graph Engineer
设计多个可验证步骤如何依赖、并行、汇合、回退和停止
```

这篇文章接着之前的[《Loop 工程：看完 Agent Loop 视频后的实践笔记》](/blog/loop-engineering-agent-loop-limited-feedback/)，把视角从“怎样做一个可靠循环”推进到“怎样组织一组可靠循环”。

## 一、先别急着画图：Loop 到底解决什么

一个最小 Agent Loop 可以写成：

```text
触发 Trigger
  ↓
执行 Task
  ↓
检查 Success Criteria
  ├─ 通过 → 结束
  └─ 失败 → 带着反馈重新执行
```

视频把 Loop 的基本组成归纳为三部分：

1. 触发器：系统何时开始运行。
2. 任务：Agent 具体要完成什么。
3. 成功标准：系统怎样判断结果是否可以接受。

这三个部分看似简单，却比“给模型一个目标，让它自己做完”严谨得多。

触发器可以是每天早上七点、收到一封邮件、代码仓库出现新 PR，或者用户按下按钮。它把一次对话变成可重复运行的系统。

任务不是一句宽泛愿望，而是一段有边界的工作。例如“收集最近二十四小时的 AI 新闻，生成带来源链接的晨报”，就比“帮我了解 AI”更适合进入循环。

成功标准决定循环有没有方向。晨报至少要包含指定栏目、满足长度限制、带原始链接，而且不能重复昨天的内容。代码修改则要通过测试、类型检查和安全扫描。

从状态转移角度看，一个 Loop 可以表达为：

$$
s_{t+1}=F(s_t,a_t,o_t,f_t)
$$

$s_t$ 是当前状态，$a_t$ 是 Agent 采取的动作，$o_t$ 是工具返回的观察，$f_t$ 是评测器给出的反馈。

只有当反馈真的能区分“更接近目标”和“只是又运行了一次”，循环才有工程价值。

因此，Loop Engineer 设计的不是 while 循环，而是一套受限反馈系统。他关心输入、工具、观察、评测、预算、停止条件和人工接管点。

## 二、晨报 Agent：一个 Loop 为什么会逐渐变重

视频里的单 Agent 每天早上七点启动，然后依次完成四类工作：

```text
读取 YouTube
→ 读取 X / Twitter
→ 读取 Reddit
→ 检查 Email
→ 汇总材料
→ 写成晨报
→ 自我检查
```

在任务规模较小时，这种设计完全合理。一个 Agent 共享同一份目标与上下文，不需要额外协议，也没有分布式协作成本。

但随着需求增长，单 Loop 会出现四种压力。

第一种是上下文压力。不同平台返回大量网页、评论、邮件和工具日志，研究过程与最终写作挤在同一个上下文窗口中。

第二种是角色冲突。一个 Agent 既负责搜索，又负责筛选、写作和审查。它很容易把“我已经找到的信息”误认为“足够完整的信息”。

第三种是串行延迟。YouTube、Reddit、邮件之间没有数据依赖，却仍然排队执行。最慢的数据源会拖长整条链路。

第四种是失败半径。假设 Reddit 抓取失败，粗糙的总循环可能重新搜索全部平台、重新生成全文，再重新审查一次。

单 Loop 的问题并不是不能完成任务，而是所有责任被压进同一个故障域：

```text
一个上下文
一个执行轨迹
一个成功判断
一个重试入口
一个很难定位的“结果不够好”
```

当系统失败时，我们只知道“晨报失败了”，却不清楚问题来自 YouTube 召回、邮件权限、信息去重、写作提示，还是审查标准。

## 三、从一个大循环，变成一张协作图

视频给出的 Graph 版本保留同一个触发器和最终目标，但把任务拆成多个专门执行者：

```text
                         ┌→ YouTube Research ┐
每天 07:00 → Dispatch ───┼→ Reddit Research  ├→ Report Writer → Reviewer
                         ├→ Social Research  ┤                  ├→ 发布
                         └→ Email Research   ┘                  └→ 修改
```

四个研究节点可以并行工作。每个节点只处理一个信息域，输出结构化摘要，再由 Writer 汇合。

Reviewer 不参与前面的写作，它独立检查报告是否满足成功标准。通过则发布；不通过则把具体问题路由给对应节点。

这里真正重要的不是“从一个 Agent 变成六个 Agent”，而是系统获得了新的控制能力：

- 无依赖的任务可以并行。
- 每个节点拥有局部上下文。
- 每一步可以有独立成功标准。
- 失败可以定位到具体节点。
- 重试可以从失败节点开始。
- 审查者可以与生产者分离。
- 不同节点可以使用不同模型、工具和预算。

可以把整张图表示为：

$$
G=(V,E,S,R)
$$

$V$ 是节点集合，$E$ 是边与路由条件，$S$ 是跨节点传递的状态，$R$ 是重试、超时与恢复策略。

Graph Engineer 的工作，就是让这四部分共同构成一个可解释、可执行、可恢复的系统。

## 四、一个关键纠正：节点不一定是 Agent

视频为了快速讲清概念，把 YouTube、Reddit、Email 等任务都画成 Agent。这种讲法直观，却不能直接当成生产系统的设计规则。

图里的节点可以是很多东西：

- 一次确定性的 API 请求。
- 一段普通 TypeScript 或 Python 函数。
- 一个 SQL 查询。
- 一个规则校验器。
- 一个人工审批步骤。
- 一个调用工具的 Agent Loop。
- 一个已经存在的外部服务。

如果某一步只需要解析 JSON、过滤日期或计算分数，就没有理由让大模型完成。

例如“确认每条新闻都包含 URL”应该是确定性验证：

```ts
function hasValidSources(items: NewsItem[]) {
  return items.every((item) => URL.canParse(item.sourceUrl))
}
```

让 Reviewer Agent 凭感觉判断链接是否存在，不仅更贵，也更不可靠。

因此，一个健康的 Agent Graph 通常是混合图：

```text
确定性触发器
→ Agent 研究节点
→ 普通代码去重
→ Agent 写作节点
→ Schema 校验
→ Agent 语义审查
→ 人工审批或自动发布
```

大模型只放在需要语义判断、开放搜索和非结构化转换的位置。其余步骤尽可能使用可测试的普通程序。

Graph Engineering 不是 Multi-Agent Engineering 的同义词。多 Agent 只是图的一种节点配置，图本身关注的是控制流、数据流和失败恢复。

## 五、Graph Engineer 真正要设计的四个对象

### 1. 节点：责任是否足够原子

节点应该有一个清晰职责、明确输入和可验证输出。

“研究所有平台并写报告”不是好节点，因为它混合了检索、筛选、综合和表达。

“找出 YouTube 上过去二十四小时内与 Agent Engineering 有关的五条高价值内容”更容易验证。

一个节点至少要声明：

```ts
type NodeContract<I, O> = {
  name: string
  input: Schema<I>
  output: Schema<O>
  timeoutMs: number
  maxAttempts: number
  success: (output: O) => Evaluation
}
```

原子化不等于无限细分。拆得过细会增加调度、序列化、模型启动和状态同步成本。

判断边界的实用问题是：这一步失败时，我们是否希望单独重跑它？如果答案是否定的，它可能不值得成为独立节点。

### 2. 边：谁在什么条件下接管

很多“Agent Graph”只有一张漂亮流程图，却没有定义边的语义。

边至少可能表达四种关系：

- 顺序依赖：B 必须等 A 的输出。
- 并行分发：A 同时触发 B、C、D。
- 汇合屏障：E 必须等 B、C、D 全部结束。
- 条件路由：评测结果决定发布、修改或人工接管。

条件边不能只写“如果不好就重试”。它需要机器可消费的原因：

```ts
type ReviewDecision =
  | { status: 'approved' }
  | { status: 'revise'; target: 'youtube'; issues: Issue[] }
  | { status: 'revise'; target: 'writer'; issues: Issue[] }
  | { status: 'human_review'; reason: string }
```

如果 Reviewer 只输出一段散文，调度器仍然不知道下一步去哪里。结构化路由结果是 Graph 从示意图变成程序的关键。

### 3. 状态：节点之间到底传什么

单 Agent Loop 可以把大量信息留在对话历史里。Graph 不能依赖所有节点共享一份隐式聊天记录。

它需要显式状态：

```ts
type MorningBriefState = {
  runId: string
  timeWindow: { from: string; to: string }
  research: {
    youtube?: ResearchBundle
    reddit?: ResearchBundle
    social?: ResearchBundle
    email?: ResearchBundle
  }
  draft?: ReportDraft
  review?: ReviewDecision
  provenance: SourceRecord[]
  budgets: BudgetLedger
}
```

状态 schema 定义了节点之间的协议。它让每个节点知道自己可以读取什么、必须写入什么，也让历史运行可以重放。

不要把每个节点的完整 prompt、网页全文和思考过程都塞进共享状态。共享状态应该保存必要事实、来源、决定和可追踪标识。

原始材料可以放对象存储或数据库，状态中只保留引用。否则 Graph 只是把单 Loop 的上下文膨胀，搬到了一个更大的 JSON 里。

### 4. 评测：成功标准放在哪一层

视频最有价值的观点是：Graph 可以为每个子任务定义成功，而不是只在最终报告上做一次模糊判断。

YouTube 节点可以检查：

- 是否至少返回五个候选来源。
- 是否全部位于时间窗口内。
- 是否保留标题、作者、URL 与发布时间。
- 是否给每条信息写出“为什么值得关注”。

Writer 节点可以检查：

- 是否覆盖全部必要栏目。
- 是否只使用研究节点提供的事实。
- 每项结论是否能回溯到来源。
- 是否符合长度、语言和格式要求。

全局 Reviewer 则关心跨节点问题，例如重复主题、证据冲突、整体叙事与风险。

局部评测回答“这个零件合格吗”，全局评测回答“这些零件组装起来是否完成了用户任务”。

## 六、为什么 Graph 可能提高质量

### 更干净的上下文

研究 YouTube 的节点不需要阅读邮件线程，邮件节点也不需要加载 Reddit 评论。每个节点都能在更小、更相关的上下文中工作。

上下文变小不自动等于结果更好。真正的收益来自信噪比提高：与当前任务无关的信息更少，工具说明与成功标准更突出。

### 更独立的审查

生产者自己审查自己的结果，会继承同一组假设和遗漏。

独立 Reviewer 可以使用不同系统提示、不同上下文，甚至不同模型。它不需要知道写作者经历了多少轮，只需要检查产物与证据。

但“换一个 Agent”也不保证独立。如果 Reviewer 只收到 Writer 的自我总结，没有看到原始标准和证据，它仍然可能被同一叙事带偏。

真正的独立审查需要独立输入：

```text
任务标准 + 结构化证据 + 最终产物
```

而不是：

```text
作者说自己做了什么 + 作者说结果为什么很好
```

### 更低的端到端延迟

假设四个研究任务分别需要 40、50、30、60 秒。

串行执行的理论研究时间是：

$$
T_{\text{serial}}=40+50+30+60=180\text{s}
$$

完全并行时，理论下界接近最慢节点：

$$
T_{\text{parallel}}\approx\max(40,50,30,60)=60\text{s}
$$

真实系统还要加调度、限流和汇合开销，但并行仍可能显著降低延迟。

并行也有代价。四个节点可能同时触发 API 限流，重复搜索相同材料，或在没有共享去重索引时产生大量冗余。

### 更小的失败半径

Reddit 节点失败时，只重试 Reddit。Writer 格式错误时，只重跑 Writer。最终审查不通过时，可以把问题路由给真正负责的节点。

局部恢复需要幂等性。如果同一个 Email 节点重试两次会重复发送消息，图的局部重试反而会制造新故障。

因此每个有副作用的节点都需要 `runId`、幂等键或提交协议。

## 七、什么时候应该从 Loop 升级到 Graph

视频给出三个非常实用的触发条件。

### 1. 上下文开始腐化

一个 Agent 每轮执行四五种任务，工具结果不断累积，旧失败、旧草稿与新状态混在一起。此时继续压缩 prompt 往往只能延后问题。

如果任务天然属于不同信息域，可以拆出局部上下文。每个节点只向下游传递结构化结论与来源。

注意，长上下文本身不是拆图理由。如果任务需要全局理解，例如通读一份完整合同并判断内部矛盾，强行分片可能丢失跨章节关系。

### 2. 需要真正独立的审查

高风险代码、财务结论、对外发布内容和安全决策，不适合完全依赖生产者自评。

这时可以把执行与审查分成两个节点，让 Reviewer 拥有独立指令、证据和拒绝权。

对于更高风险任务，Reviewer 仍不能替代人类责任。Graph 应该把 `human_review` 设计成合法终点，而不是把人工介入视为系统失败。

### 3. 存在值得并行的独立任务

多个数据源、多个候选方案、多个代码模块或多个评测维度之间没有前置依赖，就可能适合并行。

并行的前提不是“任务很多”，而是“任务之间的信息依赖足够弱”。

如果 B 的正确执行依赖 A 的结论，强行同时启动只会让 B 在缺失上下文的情况下猜测。

## 八、视频之外，还应该增加两个判断条件

### 4. 失败需要局部恢复

当一次完整运行很贵，而故障通常只发生在局部步骤时，Graph 的 checkpoint 与局部重试很有价值。

例如报告已完成研究和去重，只在发布到 Notion 时失败。可靠系统应该从发布节点恢复，而不是重新消耗一次全部研究预算。

### 5. 不同步骤需要不同能力与权限

搜索节点需要联网，但不应该拥有生产数据库写权限。发布节点需要写入权限，却不需要任意浏览网页。

代码分析可以使用擅长长上下文的模型，简单分类可以用小模型，最终审查再使用更强模型。

Graph 让能力、成本与权限沿节点边界分配。安全边界不再只能覆盖整个 Agent 进程。

## 九、什么时候不要使用 Graph

视频最后给出的判断很克制：如果你不确定是否需要 Graph，答案很可能是不需要。

以下任务通常先用单 Loop：

- 步骤少，且必须共享同一上下文。
- 总运行时间已经足够短。
- 一个确定性测试就能判断成功。
- 失败后从头重跑很便宜。
- 没有独立权限和模型配置需求。
- 团队还无法观测单 Agent 的运行轨迹。

Graph 会引入真实成本：

- 节点协议与状态 schema。
- 调度器和持久化。
- 并发控制与速率限制。
- 版本兼容与迁移。
- 分布式日志和 trace。
- 部分成功、超时和取消语义。
- 更复杂的测试组合。

如果单 Loop 的问题只是提示词模糊或评测缺失，把它拆成 Graph 不会解决根因。模糊任务会变成多个模糊节点，错误成功标准会被复制到整张图。

先把一个 Loop 做可靠，再考虑连接多个 Loop。

## 十、从 Loop 迁移到 Graph 的五步方法

### 第一步：记录真实轨迹

不要先凭想象画架构图。先记录单 Agent 的几次完整运行：

- 它调用了哪些工具。
- 哪些步骤重复出现。
- 哪些步骤最慢。
- 哪些输出占用最多上下文。
- 失败通常发生在哪里。
- 哪些步骤失败后会导致全部重跑。

Graph 的候选节点应该来自真实轨迹中的稳定责任，而不是来自组织结构或热门框架的示例。

### 第二步：识别边界

为每个候选步骤写出输入、输出、成功标准和副作用。

如果写不清输出 schema，说明节点边界可能仍然太模糊。

如果两个步骤每次都要读取彼此全部上下文，它们可能不应该拆开。

### 第三步：先抽确定性节点

优先把日期过滤、格式转换、schema 校验、去重、缓存和发布操作变成普通函数。

这样做通常比先增加第二个 Agent 更有价值，因为它立即减少模型需要承担的职责。

### 第四步：只并行真正独立的分支

先画数据依赖，再决定并发：

```text
时间窗口
  ├→ YouTube
  ├→ Reddit
  └→ Email

全部完成
  ↓
去重与冲突检测
  ↓
写作
```

汇合节点要明确处理三种情况：全部成功、部分成功、全部失败。

晨报是否允许在 Reddit 暂时不可用时降级发布？这个产品决定必须写进图，而不能留给运行时临场猜测。

### 第五步：增加独立审查与局部回退

Reviewer 的输出必须能驱动路由。

如果缺少来源，只回退到研究节点；如果结构混乱，只回退到 Writer；如果证据冲突或风险过高，则转人工。

```text
Reviewer
  ├─ approved       → Publish
  ├─ missing_source → Research Node
  ├─ poor_structure → Writer
  └─ high_risk      → Human Review
```

这比“不通过就整张图再跑一遍”更快、更便宜，也更容易分析失败。

## 十一、一个更接近生产环境的晨报图

把前面的原则合在一起，可以得到下面这条流程：

```text
Scheduler
  ↓
Create Run + Freeze Time Window
  ↓
Fan Out
  ├→ YouTube Agent ─→ Source Validator ┐
  ├→ Reddit Agent  ─→ Source Validator ┤
  ├→ Social Agent  ─→ Source Validator ┼→ Merge
  └→ Email Tool    ─→ Privacy Filter   ┘
                                           ↓
                                  Deduplicate + Rank
                                           ↓
                                      Writer Agent
                                           ↓
                                   Schema / Link Check
                                           ↓
                                     Reviewer Agent
                                  ┌────────┼─────────┐
                               Approve   Revise    Escalate
                                  ↓         ↓          ↓
                               Publish  Target Node   Human
```

这里有几个容易忽略的设计。

时间窗口在运行开始时冻结。否则不同节点可能在不同时刻查询“最近二十四小时”，导致结果边界不一致。

来源校验与隐私过滤是确定性节点。它们不需要 Agent 自由发挥。

Merge 不只是拼接数组，还负责标记缺失分支。Writer 应该知道“Reddit 无数据”与“Reddit 节点失败”不是同一件事。

发布是有副作用的节点，必须幂等。同一个 `runId` 无论重试多少次，都只能生成一份晨报。

## 十二、Graph Engineer 的观测面板应该看到什么

单 Loop 常见日志是一个不断增长的对话记录。Graph 需要同时观察节点与整次运行。

至少应该记录：

| 维度 | 应记录的信息                                 |
| ---- | -------------------------------------------- |
| 运行 | `runId`、触发来源、开始与结束时间、最终状态  |
| 节点 | 输入版本、输出引用、耗时、重试次数、错误类型 |
| 模型 | 模型名称、token、成本、工具调用、截断与限流  |
| 路由 | 选择了哪条边、判断依据、评测结果             |
| 证据 | 来源 URL、抓取时间、内容指纹、引用关系       |
| 人工 | 谁批准、修改了什么、为什么覆盖系统决定       |

只记录“节点成功”不够。一个节点可能技术上返回 200，却只找到两条低质量来源。

只记录最终质量也不够。报告变差时，需要知道是召回下降、模型变化、输入分布变化，还是 Reviewer 放宽了标准。

Graph Engineer 关注的核心指标也不只是成功率：

$$
\text{Useful Run Rate}
=
\frac{\text{无需人工返工且满足证据标准的运行数}}
{\text{全部运行数}}
$$

还应同时观察端到端延迟、单节点失败率、平均重试次数、降级发布比例、人工接管率和每次有效运行成本。

## 十三、Loop Engineer 与 Graph Engineer 的能力边界

Loop Engineer 关注一个执行者内部的闭环：

- 怎样组织上下文。
- 怎样选择工具。
- 怎样接收观察。
- 怎样根据反馈修正。
- 怎样限制预算。
- 怎样安全停止。

Graph Engineer 关注多个执行单元之间的协作：

- 怎样切节点边界。
- 怎样定义状态协议。
- 怎样表达依赖和条件路由。
- 怎样并行与汇合。
- 怎样局部重试和恢复。
- 怎样隔离权限与故障。
- 怎样追踪跨节点因果链。

二者不是替代关系。

```text
可靠节点 = 一个设计良好的 Loop
可靠系统 = 一组可靠节点 + 清晰的 Graph
```

如果节点内部没有稳定循环，Graph 只是在编排不稳定行为。如果图没有明确协议，再优秀的单 Agent 也会被错误数据、重复调用和模糊交接拖垮。

## 十四、不要从框架开始，要从失败开始

看到 Graph Engineering，很多人的下一步是选择 LangGraph、Temporal、n8n、CrewAI 或某个多 Agent 框架。

框架很重要，但它不替你决定正确节点边界，也不知道什么叫业务成功。

可以先阅读[《Tau 对比 LangGraph》](/blog/tau-vs-langgraph-agent-harness-orchestration/)，区分 Agent Harness 与工作流编排框架。前者解决一个 Agent 怎样运行，后者解决多个状态与步骤怎样可靠协作。

也可以结合[《Pi Agent 深度解析》](/blog/pi-agent-deep-dive/)，观察一个尽量薄的 Agent Core 如何提供工具循环，再思考哪些工作应该留在 Loop 内，哪些应该上移到 Graph。

真正的起点应当是一次具体失败：

- 因为上下文太杂，模型遗漏关键证据。
- 因为串行研究，任务耗时过长。
- 因为自己审查自己，错误被反复认可。
- 因为一个数据源失败，整条任务重新执行。
- 因为权限过大，研究节点也能修改生产数据。

先描述失败，再选择最小结构改变。也许答案是增加一个确定性校验器，也许是拆出一个 Reviewer，也许才是一张完整的多分支 Graph。

## 十五、最后的判断

Graph Engineering 不是 Loop Engineering 的“下一代替代品”。它更像是 Loop 规模化之后出现的系统工程。

Loop 回答：

> 一个 Agent 怎样根据反馈持续接近目标？

Graph 回答：

> 多个执行单元怎样在明确依赖、状态协议和质量门槛下共同完成目标？

视频把 Graph 概括成“连接起来的多个 Loop”，这是一个很好的入门心智模型。

工程上还要再补一句：

> 一张可靠的 Graph，不只是连接多个 Agent，而是连接多个可验证、可恢复、权限受限的工作单元。

如果一个 Loop 已经能低成本、快速、可靠地完成任务，就继续使用它。

当上下文腐化、独立审查、并行延迟、局部恢复或权限隔离成为真实瓶颈时，再把稳定的 Loop 提升为 Graph 节点。

不要为了画图而画图，也不要为了多 Agent 而多 Agent。

从最小闭环开始，从真实失败中寻找边界，再让图只承担循环已经承担不了的复杂性。这才是从 Loop Engineer 走向 Graph Engineer 的工程路径。
