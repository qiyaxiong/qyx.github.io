## 二、当前 Pi 不是“四层蛋糕”，而是核心链加边界包

当前仓库包含 `ai`、`agent`、`coding-agent`、`tui`、`telemetry`、`protocol`、`client`、`server` 和 `evals`。因此，把所有内容继续压成四层，会隐藏真实依赖。

从各包的 `package.json` 看，最重要的执行主链是：

```text
pi-ai
  ↑
pi-agent-core
  ↑
pi-coding-agent ──→ pi-tui
       │
       ├──────────→ pi-client ──→ pi-protocol
       └──────────→ pi-telemetry

pi-server ────────→ pi-ai + pi-protocol
pi-evals           独立评测入口
```

这里的箭头表示“调用方依赖被调用方”，不是概念上的上下级。

`pi-ai` 统一模型、消息、流事件和认证。`pi-agent-core` 只关心对话状态、循环、工具与事件。`pi-coding-agent` 再把文件工具、Session、资源加载、扩展和交互入口组合起来。

`tui` 是一种界面，不是 Agent 内核。`protocol/client/server` 则说明 Pi 已开始形成远程会话边界，也不能再被塞进传统四层图里一笔带过。

这个结论来自真实依赖，不来自仓库宣传语。相应源码入口可从 [packages 目录](https://github.com/earendil-works/pi/tree/853a80d26c90a14c1886f0ebb8ffaae133ca2185/packages) 逐个复核。

## 三、沿一次请求走完整调用链

现在只跟一个场景：用户输入“读取配置文件并解释”。先不讨论插件哲学，也不讨论记忆系统，只看这句话如何变成模型请求和工具调用。

### 3.1 会话不是在 `Agent` 构造函数里凭空出现

SDK 入口是 [`createAgentSession()`](https://github.com/earendil-works/pi/blob/853a80d26c90a14c1886f0ebb8ffaae133ca2185/packages/coding-agent/src/core/sdk.ts#L173)。它依次准备：

1. 工作目录和 Agent 数据目录；
2. `ModelRuntime`、`SettingsManager`、`SessionManager`；
3. `DefaultResourceLoader`，并立即执行 `reload()`；
4. 恢复历史模型、Thinking 等级与消息；
5. 创建 `Agent`；
6. 最后创建 `AgentSession`。

源码还给出了默认工具：`read`、`bash`、`edit`、`write`。这比“Pi 是一个会写代码的 Agent”更具体：它的默认最小操作面就是这四个工具。

```ts
const defaultActiveToolNames = ["read", "bash", "edit", "write"]

agent = new Agent({
  model,
  tools: [],
  streamFn: (...) => modelRuntime.streamSimple(...),
})

const session = new AgentSession({
  agent,
  sessionManager,
  resourceLoader,
  modelRuntime,
})
```

注意 `Agent` 创建时工具数组仍为空。工具、Prompt 和扩展由 `AgentSession` 周围的装配逻辑接入。这说明 `Agent` 是执行内核，而 `AgentSession` 是面向编码产品的编排边界。

### 3.2 `prompt()` 只负责建立一次运行

用户输入最终进入 [`Agent.prompt()`](https://github.com/earendil-works/pi/blob/853a80d26c90a14c1886f0ebb8ffaae133ca2185/packages/agent/src/agent.ts#L347)。这里先检查是否已有活动运行，再把字符串转成用户消息。

真正进入循环的是 `runPromptMessages()`：

```ts
await runAgentLoop(
  messages,
  this.createContextSnapshot(),
  this.createLoopConfig(options),
  (event) => this.processEvents(event),
  signal,
  this.streamFunction
)
```

这段调用暴露了 Agent Loop 的六个输入：新消息、上下文快照、运行配置、事件接收器、取消信号和模型流函数。

因此，Loop 并不直接读取 UI，也不直接认识 OpenAI。UI 通过事件观察它，模型差异由 `streamFunction` 隔离，取消则通过 `AbortSignal` 协作完成。

### 3.3 一个 Turn 内部可能经历多个模型 Step

[`runAgentLoop()`](https://github.com/earendil-works/pi/blob/853a80d26c90a14c1886f0ebb8ffaae133ca2185/packages/agent/src/agent-loop.ts#L96) 先追加 Prompt，再发出 `agent_start`、`turn_start` 与消息事件。

内部 `runLoop()` 有两层循环：

```text
外层：自然停止后，检查 follow-up
  └─ 内层：只要还有 tool call 或 steering，就继续请求模型
```

所以，“一次用户提问”不等于“一次模型请求”。只要模型持续请求工具，同一个用户任务就会经历：模型 → 工具 → 模型 → 工具 → 模型。

<AgentTurnTimeline />

在这里可用三个层级理解时间线：

| 层级    | 回答的问题                     |
| ------- | ------------------------------ |
| Session | 这段长期对话属于谁？           |
| Turn    | 哪次外部输入触发了这一轮工作？ |
| Step    | 这个 Turn 内是第几次模型推进？ |

Pi 的事件名称未必全部直接使用 `Step`，但调用结构已经体现了这个边界。DSH 与 qi-pi 则把 `turn`、`step` 明确写进持久事件。

### 3.4 Tool Call 不是从模型字符串直接调用函数

模型响应完成后，Loop 从 Assistant 内容里筛出工具调用，再进入 [`executeToolCalls`](https://github.com/earendil-works/pi/blob/853a80d26c90a14c1886f0ebb8ffaae133ca2185/packages/agent/src/agent-loop.ts#L409)。

这条路径至少经过四步：准备调用、执行工具、收尾结果、生成 `toolResult` 消息。失败也会被转成模型能够继续读取的结果，而不是简单抛出后终止整段对话。

当前实现同时支持串行与并行。只要配置要求串行，或某个工具声明串行模式，就按顺序执行；否则可并发执行，再按原调用顺序写回结果。

这个细节很重要。并行提升速度，但结果顺序仍要稳定，否则同一次模型输出的多个 Tool Call 会在不同运行中形成不同上下文。

### 3.5 自然停止并不一定代表整个 Agent 结束

一次工具链结束后，Loop 会先读取 Steering。没有工具和 Steering 时，它才到达“自然停止点”，然后再检查 Follow-up。

Steering 更像“改变当前正在进行的任务”；Follow-up 更像“当前任务结束后，再开始下一段输入”。两者共用队列会让时序变得含糊，因此源码将它们拆开。

最终调用链可以收敛为：

```text
createAgentSession
  → AgentSession.prompt
  → Agent.prompt
  → runAgentLoop
  → streamAssistantResponse
  → ModelRuntime.streamSimple
  → Assistant tool call
  → executeToolCalls
  → Tool result message
  → 下一次模型请求或 agent_end
```

## 四、`pi-ai` 如何把 Provider 差异挡在 Loop 外面

Agent Loop 接收的是 `StreamFn`，而不是某个供应商 SDK。SDK 装配时，这个函数被连接到 `ModelRuntime.streamSimple()`。

在 [`models.ts`](https://github.com/earendil-works/pi/blob/853a80d26c90a14c1886f0ebb8ffaae133ca2185/packages/ai/src/models.ts#L690) 中，`streamSimple()` 做三件事：找到 Provider、应用认证、调用 Provider 的同名流接口。

```ts
return lazyStream(model, async () => {
  const provider = this.requireProvider(model)
  const { requestModel, requestOptions } = await this.applyAuth(model, options)
  return provider.streamSimple(requestModel, context, requestOptions)
})
```

这不是“把所有 API 请求参数做成完全一样”。真正统一的是 Agent 所看到的输入输出边界：模型、上下文、选项和标准化流事件。

供应商仍可以保留自己的认证、模型能力、Thinking 表达和请求格式。统一层负责把这些差异转换成 Loop 能消费的消息与事件。

Pi 还允许扩展注册 Provider。`ModelRuntime` 保存运行时 Provider，`ExtensionRunner` 把扩展注册动作接到模型注册表。这说明 Provider 不是写死的枚举，而是可扩展能力。

但要注意一条边界：Provider 可扩展，不代表它应该直接修改 Session。它负责模型 I/O；消息落盘、分支和恢复属于上层会话语义。

## 五、Session 为什么不是普通聊天数组

Pi 的 [`SessionManager`](https://github.com/earendil-works/pi/blob/853a80d26c90a14c1886f0ebb8ffaae133ca2185/packages/coding-agent/src/core/session-manager.ts#L856) 同时维护文件条目、ID 索引和当前叶子指针。

每次 `appendMessage()` 都生成带 `id`、`parentId` 和时间戳的条目，然后把叶子推进到新条目。

```ts
const entry = {
  type: 'message',
  id: generateId(this.byId),
  parentId: this.leafId,
  timestamp: new Date().toISOString(),
  message
}
```

这已经不是简单的 `messages.push()`，而是一棵以父指针连接的追加式会话树。

### 5.1 Branch 的本质是移动叶子

[`branch()`](https://github.com/earendil-works/pi/blob/853a80d26c90a14c1886f0ebb8ffaae133ca2185/packages/coding-agent/src/core/session-manager.ts#L1355) 不复制旧历史，也不删除失败路径。它把 `leafId` 移到旧条目，下一次追加自然形成新分支。

```text
A → B → C → D
        └→ E → F
```

当叶子从 `D` 移回 `B`，新消息 `E` 的 `parentId` 指向 `B`。旧的 `C → D` 仍留在文件中，因此可以审计、导出或再次导航。

![Pi Session 追加式会话树](/images/blog/pi-agent/pi-agent-session-tree.webp)

### 5.2 Compaction 改变模型看到的表面，不抹掉原始事实

长对话会超过上下文窗口。Pi 的压缩逻辑为旧路径生成摘要，让后续模型请求读取“摘要 + 较新消息”。

正确理解不是“把历史删短”，而是“从完整历史投影出一个较短的模型表面”。原始条目仍留在 Session 文件里。

这也解释了为什么 Branch Summary 和 Compaction Summary 是独立条目，而不是伪装成普通用户消息。它们描述的是会话结构变化，不只是聊天内容。

## 六、ResourceLoader 与 Extension 到底负责什么

[`ResourceLoader` 接口](https://github.com/earendil-works/pi/blob/853a80d26c90a14c1886f0ebb8ffaae133ca2185/packages/coding-agent/src/core/resource-loader.ts#L40) 同时暴露 Extension、Skill、Prompt、Theme、上下文文件和系统 Prompt。

`DefaultResourceLoader.reload()` 会重新加载设置、解析 Package 来源、筛选启用资源并记录诊断信息。项目级扩展还会经过信任判断。

这说明 Pi 的“扩展”至少有两类：

- 代码能力：Provider、工具、命令、事件处理器；
- 内容资源：Skill、Prompt、Theme、AGENTS.md 等上下文文件。

两者都可被发现和重载，但风险完全不同。读取一份 Prompt 与执行一个本地 TypeScript 扩展，不应该共享相同信任等级。

### 6.1 注册为什么必须可撤销

热重载最常见的错误不是“新代码没加载”，而是旧监听器仍在。结果是同一个事件执行两次、同名工具冲突，或者旧 Provider 继续占用资源。

因此注册行为必须绑定 Extension 生命周期：

```text
mount extension
  → register tool / event / provider
  → 保存对应 disposer

dispose extension
  → 撤销注册
  → 释放资源
```

Pi 当前提供了丰富的 Extension API，但它仍更接近“Coding Agent 的扩展宿主”。它没有把所有运行时能力都统一建模为 Context Service。

## 七、把 oh-my-pi、DSH 与 qi-pi 放回源码坐标系

项目对比不能只列功能勾选。更有意义的问题是：它们在原始调用链的哪个位置加深了设计？

### 7.1 oh-my-pi：沿 Pi 主链向产品工程扩张

oh-my-pi 仍能看到 `ai`、`agent`、`coding-agent` 和 `tui`，但仓库已扩展出更多专用包：

| 包              | 从源码描述看解决的问题                    |
| --------------- | ----------------------------------------- |
| `hashline`      | 带行锚点的紧凑 Patch 语言与应用器         |
| `mnemopi`       | 本地 SQLite Memory Engine                 |
| `snapcompact`   | 面向视觉模型的位图帧上下文压缩            |
| `natives`       | PDF、音频、PTY、grep、图像等原生能力      |
| `stats`         | 本地模型用量观察面板                      |
| `browser-relay` | 驱动用户现有 Chrome 标签页                |
| `metaharness`   | 评测运行、存储、REST/SSE 与 Web Dashboard |

这些判断来自各包的 [`package.json`](https://github.com/can1357/oh-my-pi/tree/33cc6b9a043a74e00a157e72ca909272796d8461/packages)，不是根据项目名字猜测。

oh-my-pi 的 Agent Loop 也明显更大，加入暂停、重试、运行收集和更复杂的工具调度。它不是另一套完全无关的 Agent，而是沿 Pi 的执行骨架做深度产品化。

### 7.2 DSH：把共享 Context 和插件生命周期放到中心

DSH 的重点不是把 Pi Loop 再写一遍，而是把 Agent、Session、Tool、Provider、Sandbox 等能力都挂到共享 Context。

其 [Cordis Primer](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef8148158c3a752a658978873241fdf8e2bbc/docs/cordis-primer.md) 给出两条核心语义：插件实现 Service；`inject` 声明依赖，缺少服务时插件等待激活。

这里必须区分两个概念：

```text
ctx.provide(service)  → 服务此刻真实存在
plugin.inject         → 插件需要哪些服务才能激活
```

`inject` 不创造服务，也不应让 Loader 推导一张静态 Service Graph。Service Truth 来自 Context 当前真实注册状态。

DSH 还把工具生命周期拆成可观察流水线。官方 [工具执行文档](https://github.com/deepseek-ai/deepseek-harness/blob/cd5ef8148158c3a752a658978873241fdf8e2bbc/docs/tool-execution-pipeline.md) 明确列出 pre-execute、Guard、execute、post-execute 和最终结果阶段。

因此，DSH 的优势不是“插件数量多”，而是注册副作用、依赖激活、工具策略和 UI 观察都有明确生命周期边界。

### 7.3 qi-pi：不是 TypeScript 项目的逐行 Python 翻译

qi-pi 借鉴 Context-first 语义，但代码已经形成自己的 Python 运行时。最小内核位于 `qi_runtime`，包括 Context、Service、Event、Plugin Activation 与 Effect Ownership。

Loader 位于运行时基础设施层，但不是不可再缩小的内核原语。源码开头直接写明：Loader 不得根据 `inject` 或 `provide` 元数据推导 Service Graph，依赖协调由 Context Registry 负责。

[`PluginLoader.reload()`](https://github.com/qiyaxiong/pi-agent-py/blob/4d8f9b4c80db1b70b6fa01a1ae0d73d3debf7bcd/packages/qi_runtime/src/qi_runtime/loader/loader.py#L201) 执行的是受影响节点事务：

```text
预解析并校验 Candidate
  → 计算增量 Cutover
  → 卸载受影响旧节点
  → 挂载受影响新节点
  → 等待 Context 生命周期稳定
  → 检查产品后置条件
  → Commit；失败则恢复旧节点
```

它不是先构造一套完整候选 Runtime 再整体交换。这种增量 Reconciliation 能保留未受影响的 Context 子树，也要求回滚逻辑更严谨。

## 八、qi-pi 如何把事件日志变成恢复基础

Pi 的 Session 是追加式会话树。qi-pi 进一步把 Session Event Log 定义为消息历史、恢复、UI 和审计的共同事实来源。

[`Session`](https://github.com/qiyaxiong/pi-agent-py/blob/4d8f9b4c80db1b70b6fa01a1ae0d73d3debf7bcd/packages/qi_session/src/qi_session/session.py#L335) 的注释很直接：内存中是 append-only log，消息历史始终从事件投影。

每个事件都有递增 `seq`，还可以携带 `turn` 与 `step`。这让错误可以定位到“哪个 Session、哪个 Turn、哪个 Step、哪次工具之后”。

```python
event = SessionEvent(
    seq=self.next_seq,
    session_id=self.id,
    type=event_type,
    data=payload,
)
```

`SessionService.read_after()` 允许按 sequence 读取增量。这正是多 Channel 断线续传的基础：客户端记住最后消费的序号，重连后只补后续事件。

```text
Web 收到 seq=827
  → 断线
  → after_sequence=827
  → 补 828、829、830……
```

### 8.1 Agent Driver 不维护第二份消息真相

[`ReactAgentDriver`](https://github.com/qiyaxiong/pi-agent-py/blob/4d8f9b4c80db1b70b6fa01a1ae0d73d3debf7bcd/packages/qi_agent_loop/src/qi_agent_loop/driver.py#L195) 每次请求都从 Session Surface 重建上下文。

它在执行前持久化具有外部意义的边界。进程重启后，Driver 读取事件并归约执行状态，再判断继续、协调工具结果，还是要求人工处理。

这与“把内存里的 messages 定期保存一下”不同。前者从持久事实恢复状态机；后者仍依赖崩溃前那份内存状态是完整的。

### 8.2 Tool Operation Ledger 解决最危险的崩溃窗口

假设工具已经向外部系统付款，但进程在保存 `tool/result` 前崩溃。重启后如果直接重跑工具，可能重复付款；如果直接标记成功，又没有证据。

qi-pi 在工具执行前写入 `tool/operation/prepared` 和 `tool/operation/dispatched`。非只读工具在真正调用前强制 flush。

工具若能返回外部回执，还可记录 `tool/operation/external-result-recorded`。恢复时再由工具的 `reconcile()` 判断已成功、失败或结果未知。

```text
prepared → flush
dispatched → external side effect
external-result-recorded → committed
```

这个 Ledger 是 qi-pi 的增强，不应描述成 Pi 或 DSH 原样提供的能力。

### 8.3 对外协议与内核不是一回事

qi-pi 面向 Blog、Web、Live2D 和管理后台等多 Channel，因此外部采用 HTTP Command、SSE Session Stream 与 DSH WebSocket。

JSON-RPC 更适合跨进程的双向控制边界，例如 Direct Codex Provider、Peer Runtime、MCP、LSP 或外部 Subagent Provider。

所以无需把整个系统改成 JSON-RPC。更清楚的分层是：

```text
Channel
  → HTTP / SSE / WebSocket Gateway
  → Runtime Protocol（必要时 JSON-RPC）
  → Agent Runtime
  → append-only Event Store
```

协议解决“如何跨边界调用”；Context、Agent Loop 和 Event Log 解决“运行时如何成立”。两者不能混成同一层。

## 九、四个项目真正的差异

| 维度     | Pi                           | oh-my-pi                    | DSH                        | qi-pi                             |
| -------- | ---------------------------- | --------------------------- | -------------------------- | --------------------------------- |
| 主语言   | TypeScript                   | TypeScript + Native         | TypeScript                 | Python                            |
| 核心关注 | 小而清晰的 Coding Agent 主链 | 沿 Pi 做产品级增强          | Context-first 插件 Harness | 多 Channel Agent Service Kernel   |
| 状态基础 | 追加式 Session Tree          | 强化后的 Session 与本地能力 | Session 事件与插件服务     | Session Event Log 唯一事实源      |
| 扩展中心 | Coding Agent Extension API   | 更丰富的产品扩展            | Context / Service / inject | Python Context / Service / Effect |
| 恢复重点 | 会话恢复、分支、压缩         | 产品运行与复杂工具链        | Turn/Step/Event 生命周期   | 状态机恢复与工具副作用协调        |
| 外部入口 | CLI/TUI，另有协议包          | CLI/TUI/Browser/Stats       | API、Web、插件 UI          | HTTP/SSE/WS，多 Channel           |

这张表不是成熟度排名。四者选择了不同的“深模块”：Pi 深在精简主链；oh-my-pi 深在终端产品；DSH 深在插件运行时；qi-pi 深在 Python 服务化与恢复语义。

## 十、如何继续读源码，而不是继续读结论

如果想验证本文，不必一次读完整个 Monorepo。按以下顺序走一遍即可：

1. 从 `createAgentSession()` 看对象如何装配；
2. 从 `Agent.prompt()` 跟到 `runAgentLoop()`；
3. 在 `executeToolCalls()` 观察工具结果怎样回到消息历史；
4. 在 `ModelRuntime.streamSimple()` 看 Provider 如何被选择；
5. 在 `SessionManager.appendMessage()` 和 `branch()` 看追加式会话树；
6. 在 `ResourceLoader.reload()` 看资源来源与信任边界；
7. 最后才对照 oh-my-pi、DSH 与 qi-pi 的加深方向。

读每个模块时都问五个问题：输入是什么、输出是什么、状态写到哪里、失败留下什么、重启后靠什么恢复。

这五个问题比“它支持多少 Agent 模式”更能判断一个 Harness 是否真正可靠。

## 结语

Pi 最值得学习的不是某个命令，而是它把模型流、Agent Loop、工具执行、资源加载和 Session 拆成可沿调用链理解的边界。

oh-my-pi 证明这条主链可以继续产品化；DSH 把插件与 Context 生命周期提升为运行时核心；qi-pi 则把这些语义重新组织成 Python、多 Channel、事件驱动且可恢复的 Agent Service Kernel。

真正有效的项目分析，也应该采用同样原则：先找到事实源，再建立投影；先解释调用路径，再谈架构理念。
