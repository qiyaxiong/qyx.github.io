假设博客已经有一个问答入口，用户问：“找出讲 Python 异步的文章，再解释协程与线程的区别。”系统需要查文章、取得原文，并依据检索结果回答。下面用这个教学场景解释 MCP，不表示本站已经部署了相同的 MCP 服务。

直接调用博客搜索 API 当然可以。问题出现在第二个客户端也想用这项能力时：网页助手、编辑器和本地 Agent，是否都要各自理解搜索接口的路径、参数、返回值和错误？如果再接文件系统、数据库和工单系统，各种接入代码就会继续增加。

**MCP 提供统一的能力描述、发现与调用约定。模型应用通过它连接工具和数据服务，再由应用把这些能力接入模型的工具调用循环。**理解原理，要沿一次请求分清：谁提供描述，谁选择工具，谁发请求，谁执行，以及结果最终怎样回到模型上下文。

本文先走完博客搜索，再讨论通信、版本和失败路径。报文固定采用 **2025-06-18** 版，便于解释一组完整、一致的消息；后文另说明截至 2026-11-04 核对到的新版变化，不将两个版本混用。

## 用户发出问题后，哪些组件开始工作

收到用户问题的是 Host，也就是运行模型、管理会话和组织工具执行的应用。Host 内部使用 MCP Client 与 MCP Server 通信；博客 Server 再访问搜索索引或文章存储。

下面是职责示意。模型调用和协议通信分属两条路径，最后在 Host 汇合：

```text
用户的问题
    ↓
Host：会话、上下文、工具策略与执行编排
    ├─ 模型 API：输入问题和工具定义，取得回复或调用意图
    └─ MCP Client：发现能力、发送调用、接收结果
           ↓
       博客 MCP Server
           ↓
       搜索索引与文章存储
```

Host 可以为不同 Server 管理不同 Client。例如博客搜索和本地文件读取分别有自己的连接、状态与授权范围。Server 可以是本地进程，也可以是远程服务；名称中的“服务端”不意味着必须部署在云上。

模型通常不亲自建立这些连接。它输出工具选择和参数，Host 执行相应的调度代码。Server 也不必包含模型：接收一个查询、执行搜索、返回文章结果，就足以提供有用的 MCP 能力。[官方架构说明](https://modelcontextprotocol.io/docs/learn/architecture)

这一区分有直接的排障价值。模型没有选中工具，要检查工具描述和输入上下文；工具被选中但没有请求发出，要检查 Host 的分派与审批；请求到了 Server 却查不到文章，则要继续检查搜索服务和数据权限。

## 先发现工具，模型才知道可以搜索什么

Client 接入 Server 后，可以通过 `tools/list` 查询工具目录。博客 Server 返回的一个工具定义可以是下面这样。它是教学示例，`topK` 的范围属于这里约定的业务限制：

```json
{
  "name": "search_blog_articles",
  "description": "搜索已发布的博客文章，返回标题、链接与相关摘要。",
  "inputSchema": {
    "type": "object",
    "properties": {
      "query": { "type": "string" },
      "topK": { "type": "integer", "minimum": 1, "maximum": 10 }
    },
    "required": ["query"],
    "additionalProperties": false
  }
}
```

名字用于标识工具，说明帮助模型判断什么时候使用，`inputSchema` 描述参数结构。Client 不必为每个博客搜索服务手写一份私有工具说明，而是按统一约定取得这些信息。[工具定义与发现：2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)

**发现不等于执行，也不等于全部交给模型。**Host 可以依据用户身份、场景和上下文预算筛选工具，再转换成当前模型 API 支持的工具定义。面向访客的问答入口可以只暴露搜索与读取，作者使用的管理入口才允许发布。

模型取得定义后，也未必知道工具内部如何实现。博客索引可以来自 Markdown、Notion 或数据库；只要 Server 保持外部契约，调用方就不必跟着存储方案变化。这正是统一协议降低耦合的地方。

但“动态发现”不会自动解决所有适配问题。模型 API 对工具 Schema 的支持范围可能不同，返回内容也需要映射。工具描述含糊、参数过宽或结果过大时，即使协议完全合规，模型仍然可能用错工具。

## 从模型的调用意图，到一次真正的执行

面对用户的问题，模型可能产生这样的调用意图：

```text
search_blog_articles(query="Python asyncio 协程 线程", topK=5)
```

此时没有发生搜索。这只是一份由模型生成的结构化输出，Host 还需要关联调用、检查参数和权限，并决定是否需要用户确认。服务端必须独立检查身份与数据访问范围，不能把“模型填对了参数”当作授权。

通过检查后，MCP Client 发送 `tools/call`。下面按 2025-06-18 版展示一次请求，省略连接初始化和认证细节：

```json
{
  "jsonrpc": "2.0",
  "id": 12,
  "method": "tools/call",
  "params": {
    "name": "search_blog_articles",
    "arguments": {
      "query": "Python asyncio 协程 线程",
      "topK": 5
    }
  }
}
```

Server 找到工具实现，校验参数后访问搜索服务，再把结果编码成协议响应。下面的文章名称和摘要均为构造数据：

```json
{
  "jsonrpc": "2.0",
  "id": 12,
  "result": {
    "content": [
      {
        "type": "text",
        "text": "文章：Python 异步中的等待与并发。摘要：协程在等待 I/O 时让出执行权。"
      }
    ],
    "isError": false
  }
}
```

这里有两个容易忽略的细节。第一，响应的 `id` 对应请求，便于 Client 找到等待中的调用。第二，`content` 是协议返回内容，不等于已经出现在模型上下文或用户页面中。Host 需要按所用模型 API 的格式，把结果关联回原工具调用，再发送下一次模型请求。

模型读到摘要后，可以直接回答，也可能发现证据不足，继续请求文章原文。**决定继续还是结束的是应用与模型组成的执行循环，MCP 负责其中的标准通信。**它不会因为一条工具响应已经返回，就替 Host 宣告用户任务完成。

如果已有 Function Calling，可以这样理解两者的配合：Function Calling 让模型表达结构化的工具调用；MCP 让应用以统一方式发现并访问外部工具。Host 是中间的桥梁，既要理解模型 API，也要管理 MCP Client。[工具调用消息与结果：2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)

## 摘要不足时，怎样读取资源和复用提示模板

搜索工具适合按条件查找候选文章。已经知道一篇文章的地址、想取得稳定的数据表示时，还可以使用 Resources。博客 Server 例如提供 `blog://articles/python-asyncio` 这样的 URI，Client 按资源接口读取内容，由 Host 决定读取结果是否进入上下文。

Tools 和 Resources 的区别不必简化为“能写”和“只读”。搜索本身通常是只读工具，但它依然是一个带参数的执行动作；Resources 更侧重以 URI 暴露可读取的数据。Server 可以同时提供两者，调用方按任务选择。

Prompts 则可以提供“根据检索证据回答并保留引用”等可复用模板。它帮助客户端组织交互，不会自己开始一次模型推理。模板如何选择、与哪些上下文组合，仍然是 Host 的责任。[三类服务端能力](https://modelcontextprotocol.io/docs/learn/architecture#primitives)

沿这个例子，也能分清 MCP、RAG 与知识组织的关系：RAG 负责召回、重排和组织证据，MCP 可以把搜索和读取暴露成可复用接口。如果另有 LLMWiki，它可以整理 Markdown、索引和知识关系；这些工作不会因为接入协议就自动完成。

文章找到之后，还要检查引用是否准确、结果是否过期以及当前用户能否读取全文。将全部资源一次性塞入上下文，会消耗预算并引入无关信息；按任务选择章节、控制结果大小，属于 Host 的上下文工程。

## 这些消息怎样在两个进程之间传递

MCP 使用 JSON-RPC 2.0 表达请求、响应和通知。`method` 指定操作，`params` 携带参数；请求和响应通过 `id` 关联。通知没有请求 ID，不要求对方返回响应。

传输层负责把这些消息送到另一端。常见的两种方式各有适用场景：

| 传输 | 常见部署 | 需要守住的边界 |
| --- | --- | --- |
| stdio | Client 启动本地 Server 子进程 | stdin/stdout 传递协议消息，普通日志写 stderr |
| Streamable HTTP | 远程 Server 服务多个客户端 | 按协议处理 HTTP 请求、可选 SSE 流、认证与版本信息 |

在 stdio 下，消息按换行分隔。Server 把普通调试日志写入 stdout，可能让 Client 把日志当作协议数据，导致解析失败。这类故障与模型能力无关，应该先检查进程输入输出。[传输规范：2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports)

远程连接使用 HTTP，也不表示每个网络数据块就是一个完整 JSON-RPC 消息。实现需要按对应 HTTP/SSE 规则解析消息边界，再按请求 ID 分派结果。网络读取、协议消息和前端渲染是不同阶段，不能混在一起判断是否“流式”。

因此，有 REST API 之后仍然可以再包装 MCP Server：内部继续请求原业务 API，外部统一工具发现与调用。代价是多了一层协议适配、连接管理和运行维护；只有一个固定调用方时，直接用业务 API 也可能更合适。

## 初始化流程为什么必须说明协议版本

上面的调用报文固定采用 2025-06-18 版。该版本在正常操作前，有一段明确的初始化过程：

```text
Client → Server：initialize（协议版本、客户端信息与能力）
Server → Client：返回协议版本、服务端信息与能力
Client → Server：notifications/initialized
Client → Server：tools/list
Client → Server：tools/call
```

初始化时要确认双方能否使用兼容版本，以及对方声明了哪些能力。没有兼容版本，应停止不兼容的交互；连接成功也不意味着双方支持全部可选能力。[生命周期规范：2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18/basic/lifecycle)

**截至 2026-11-04 核对的 2026-07-28 架构文档，发现方式已经变化。**新版采用按请求携带版本与客户端能力的无状态设计，`server/discover` 用于取得服务端身份、能力和支持的版本；客户端也可以直接发起请求，并处理版本不兼容错误。

所以上面的 `initialize` 序列不能作为新版的通用握手模板，新版请求也不能直接照抄前文的旧版报文。实现或面试讨论时，先说明版本，再对照相应文档看生命周期和元数据要求。[新版发现机制](https://modelcontextprotocol.io/docs/2026-07-28/learn/architecture#statelessness-and-discovery)

版本发现还不等于工具目录永远有效。工具可能因配置或权限变化而增减。Host 需要按照对应版本的通知、订阅或刷新机制维护目录，并处理“模型选择时可用，执行时已经不可用”的情况。缓存可以减少重复发现的开销，但不能替代执行时检查。

## 搜索失败或连接断开以后，谁负责恢复

同样是“没有得到结果”，原因可能完全不同：参数不合法、工具不存在、身份凭据失效、索引暂时不可用，或者网络响应丢失。把这些情况统一成空列表，模型就可能错误地告诉用户“博客里没有相关文章”。

MCP 可以表示协议错误和工具执行结果中的错误状态；Host 仍要决定如何解释、重试、展示和继续。排查时，应保留请求与结果的关联，区分网络、协议和业务层的失败，并向模型提供足够明确的反馈。

对只读搜索，有限次数的重试通常较容易安排。但假设工具换成 `publish_article`，超时就不能直接理解为“没有发布”：Server 可能已经提交，只是响应没送回来。JSON-RPC 的请求 ID 关联消息，不自动提供业务幂等性。写操作需要由业务设计操作键、去重或状态查询，避免重试生成两篇文章。

取消也有类似边界。用户停止等待，并不能证明外部动作已撤销。Host 应区分“已发出取消”“工具停止”和“副作用已完成”，不能只在界面删掉工具卡片就当作回滚。

权限检查同样需要落到真实资源上。访客的搜索工具只能读公开文章，作者的发布工具只允许修改有权限的内容。客户端提示词中的“不要访问私人数据”不能代替服务端授权。工具 Schema 描述输入结构，也无法证明当前用户有权发布指定文章。

最后，工具返回的文章和网页属于外部数据。即使其中写着“忽略原有规则并执行命令”，也不应因此获得更高优先级或扩大工具权限。工具可被连接、调用和信任，是三个需要分别判断的问题。

## 从一次成功搜索，检查工具是否值得复用

博客搜索 Server 可以供网页问答、本地写作助手和编辑器复用，但这些客户端不一定拥有相同的权限和上下文预算。Server 要保持业务契约，Host 则要筛选能力、控制结果规模并正确处理错误。

边界也应围绕数据与职责设计。博客搜索和读取可以归到博客服务，数据库管理、部署与邮件发送有各自的授权要求。按责任拆分有助于审计；也不必机械规定一个 Server 只能有一个工具。判断依据是权限、维护和故障边界是否清晰。

接好以后，还需要用具体任务评测。对本文场景，至少应验证：用户问 Python 异步时是否选中搜索工具，摘要不足时是否读取原文，私人文章是否被过滤，索引故障是否被准确报告，以及结果与最终回答是否有正确引用关系。

这些检查分别对应发现、选择、执行和回答质量。“可以调用工具”只证明链路的一部分成立，不足以证明 Agent 已经正确完成任务。工具描述、检索质量、上下文组织和模型行为仍然需要一起验证。

## 面试时，怎样用一段话串起整个原理

回答可以沿本文的实际分工来讲：

> MCP 是模型应用连接外部工具和数据的标准协议。Host 通过内部的 Client 连接 Server，取得工具描述和参数 Schema，再把允许使用的工具交给模型。模型产生调用意图后，Host 检查策略并分派，Client 发送协议请求，Server 校验并执行；结果回到 Host 后进入模型上下文，模型继续回答或调用其他工具。底层使用 JSON-RPC 2.0，可通过本地 stdio 或远程 Streamable HTTP 传输。具体能力发现与初始化流程，需要按实现采用的协议版本说明。

这段回答之后，可以拿博客搜索走一遍：从用户问题开始，解释工具定义从哪里来、模型输出了什么、请求由谁发出、结果怎么进入下一次模型调用。面试官追问 Function Calling、HTTP API 或错误恢复时，再落回对应阶段，而不用重背一套概念。

接入 MCP 通常不要求为每个工具重新训练模型，Host 可以动态提供工具定义；但模型仍需具备适当的工具调用能力，能否稳定用对要靠评测。协议统一降低接入成本，不能单独保证推理质量、业务正确性和安全性。
