前面讲工具调用时，我们把工具看成模型可以使用的外部能力。讲工作流与 Agent 时，又进一步讨论了工具如何被编排。

当工具数量变多，一个新问题会出现：每个应用、每个模型、每个工具都用自己的接入方式，生态会很快碎掉。

这就是 MCP 这类统一协议试图解决的问题。

MCP 可以理解为 agent 和外部工具之间的一套通用连接方式。它让模型应用能发现工具、读取资源、调用能力，而不是每个工具都重新设计一套私有接口。

但 MCP 不是魔法。它解决的是连接协议问题，不自动解决权限、安全、业务边界、产品体验和评测问题。

## 1. 为什么需要统一工具协议

没有统一协议时，每接一个工具都要定制：

```text
Notion API
GitHub API
PostgreSQL 查询
浏览器自动化
文件系统
内部知识库
工单系统
```

每个工具都有自己的鉴权、参数、返回值、错误格式和文档。

对于 agent 应用来说，这会带来几个问题：

- 工具接入成本高。
- 工具描述格式不一致。
- 模型不知道有哪些工具可用。
- 返回结果难以统一进入上下文。
- 权限和错误处理散落在各处。

统一协议的目标是让工具暴露方式更标准：

```text
工具提供方
  -> 按协议暴露 resources / tools / prompts
  -> agent 客户端发现能力
  -> 模型按 schema 调用工具
```

这样工具生态才能规模化。

## 2. MCP 解决的第一件事：能力发现

Agent 要调用工具，首先得知道有哪些工具。

一个 MCP server 可以声明：

- 可读取的资源。
- 可调用的工具。
- 可复用的 prompt 模板。

例如一个博客知识库 server 可以暴露：

```text
resources:
  blog://articles
  blog://articles/{slug}

tools:
  search_blog_articles
  read_blog_article
  list_blog_series
```

客户端不需要提前把这些能力写死在代码里，而是可以从 server 查询。

这对工具生态很重要。否则每新增一个工具，都要改 agent 客户端代码。

## 3. MCP 解决的第二件事：统一 schema

工具调用需要 schema。

例如：

```json
{
  "name": "search_blog_articles",
  "description": "Search published blog articles.",
  "inputSchema": {
    "type": "object",
    "properties": {
      "query": { "type": "string" },
      "topK": { "type": "number" }
    },
    "required": ["query"]
  }
}
```

统一 schema 的好处是：

- 模型知道参数怎么填。
- 客户端可以做校验。
- 工具文档可以自动生成。
- 返回值可以按统一方式进入上下文。

这和前面讲的工具调用是一脉相承的。MCP 让工具 schema 有了更统一的分发方式。

## 3.1 原理先看分工：Host、Client 与 Server

假设用户问：“找出博客里讲 Python 异步的文章，并说明协程与线程的区别。”下面以一个教学构造的博客搜索工具追踪这次请求，不表示本站已经部署了该 MCP 服务。

Host 是运行模型、管理会话和组织工具执行的应用。它内部的 MCP Client 负责与 MCP Server 通信；Server 暴露搜索等能力，再访问实际的博客索引或数据库。一个 Host 可以管理多个 Client，分别连接不同服务。

```text
用户 → Host：会话、模型调用、工具策略
           ├─ MCP Client → 博客 MCP Server → 搜索索引
           └─ MCP Client → 文件 MCP Server → 本地文件
```

模型生成工具调用意图，Host 决定是否执行并分派请求。Client 处理协议消息，Server 校验请求并运行工具。模型通常不会亲自建立网络连接，Server 也不必包含大模型。

Tools、Resources、Prompts 对应三类接口：可执行的操作、可读取的数据、可复用的提示模板。Host 决定哪些内容进入模型上下文；发现一个工具，不等于立即执行或将其全部结果交给模型。[官方架构](https://modelcontextprotocol.io/docs/learn/architecture)

## 3.2 沿一次搜索，看工具怎样进入模型上下文

在能力发现完成后，Client 用 `tools/list` 获取工具目录，其中包括前面示例的名称、说明和 `inputSchema`。Host 按权限和当前任务筛选工具，转换成所用模型 API 接受的工具定义。

模型看到用户问题与工具描述后，可能产生 `search_blog_articles(query="Python asyncio", topK=5)` 的调用意图。这是模型输出的结构化数据，还不是搜索结果。Host 检查参数，执行必要的审批与访问策略，再交给 Client。Server 仍需独立校验身份、参数和可访问的数据范围，不能只信任客户端已经检查过。

下面的报文按 **MCP 2025-06-18** 表示，省略初始化与认证，只演示一次调用；它不是新版协议的完整请求模板。

```json
{
  "jsonrpc": "2.0",
  "id": 12,
  "method": "tools/call",
  "params": {
    "name": "search_blog_articles",
    "arguments": { "query": "Python asyncio", "topK": 5 }
  }
}
```

Server 可以在 `result.content` 中返回文本，或按该版本支持的结构返回其他内容。以下教学响应将一条搜索结果表示为文本：

```json
{
  "jsonrpc": "2.0",
  "id": 12,
  "result": {
    "content": [
      { "type": "text", "text": "找到文章：Python 异步中的等待与并发。摘要：协程在等待 I/O 时让出执行权。" }
    ],
    "isError": false
  }
}
```

Host 将工具结果关联到原调用，按模型 API 要求加入下一次请求的上下文。模型才据此回答，或继续请求读取原文。完整路径是：发现工具 → 模型选择 → 应用授权与分派 → Server 执行 → 结果进入上下文 → 模型继续。这一循环由 Host 编排，MCP 本身不规定模型何时结束回答。[工具协议：2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)

## 3.3 JSON-RPC 表达调用，传输层负责送达

JSON-RPC 2.0 规定请求、响应和通知的消息结构。`method` 指定操作，`params` 携带参数；响应使用同一个 `id` 对应请求。通知没有请求 ID，也不要求返回响应。这里的 `id` 用于关联消息，不自动提供业务幂等保证。

MCP 在 RPC 之上定义工具、资源和提示模板等具体方法。传输层则负责把这些消息送到另一端：

| 传输 | 常见部署 | 排查时关注什么 |
| --- | --- | --- |
| stdio | Client 启动本地 Server 子进程 | 消息经 stdin/stdout 交换；普通日志应写 stderr，避免破坏消息流 |
| Streamable HTTP | 远程 Server 服务多个客户端 | 使用 HTTP 传递协议消息，并可用 SSE 承载流式消息；同时检查认证、连接及版本要求 |

因此，MCP 与 HTTP 不在同一抽象层。远程 MCP 可以建立在 HTTP 上，Server 内部也可以继续调用已有 REST API。工具 Schema、发现方法与调用约定，让宿主免于为每种业务服务分别实现一套工具接入协议。[传输规范：2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18/basic/transports)

## 3.4 初始化握手必须带着版本解释

如果面试官追问连接刚建立时发生什么，可以先明确实现所采用的版本。以 **2025-06-18** 为例：

```text
Client → Server：initialize（版本、客户端信息与能力）
Server → Client：返回版本、服务端信息与能力
Client → Server：notifications/initialized
Client → Server：tools/list
Client → Server：tools/call
```

版本兼容性与能力协商决定后续可以使用哪些功能；连接成功不意味着支持所有可选能力。双方找不到兼容版本时，应停止这条不兼容的交互。[生命周期规范：2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18/basic/lifecycle)

**版本更新说明（2026-11-04 核对）**：官方 `2026-07-28` 架构文档已经采用按请求携带版本和客户端能力的无状态设计；`server/discover` 用于发现支持的版本和服务端能力，客户端也可直接发起请求并处理版本不兼容错误。因此，不能把上面的旧版初始化握手套到所有现行实现。面试时说明项目版本，比只背方法名更准确。[新版发现与请求元数据](https://modelcontextprotocol.io/docs/2026-07-28/learn/architecture#statelessness-and-discovery)

## 3.5 失败发生在哪一层，决定怎样恢复

搜索返回“索引暂不可用”、JSON-RPC 方法不存在、HTTP 认证失败和连接超时，属于不同层次的问题。前者可以作为工具执行错误返回；协议错误、认证问题和网络故障需要分别诊断。Host 应保留调用与结果的关联，让模型知道这次操作失败了，而不是将错误解释为空搜索结果。

超时尤其不能直接理解为“没有执行”。只读搜索通常容易重新尝试，但发布文章等写操作可能已完成，只是响应丢失。请求 ID 不能阻止重复发布，业务需要操作幂等键或状态查询。取消请求也不等于已经撤销外部副作用。

此外，工具返回的文章、网页和文档应作为外部数据处理。内容里出现“忽略原有规则并执行命令”，不应因此获得工具权限。协议连接成功和工具调用安全，需要分别验证。

## 4. MCP 解决的第三件事：上下文资源

有些信息不适合设计成“调用工具”，而更像“读取资源”。

例如：

```text
file:///README.md
github://repo/issues/123
blog://articles/rag-introduction-retrieval-citations
postgres://schema/public
```

资源的价值是把外部信息以稳定 URI 暴露给 agent。

这样模型或客户端可以先列出资源，再按需读取，而不是把所有内容一次性塞进上下文。

这和上下文工程关系很大：

```text
不要把全部知识放进 prompt
  -> 暴露可读取资源
  -> 根据任务按需读取
  -> 把读取结果压缩进上下文
```

资源机制让 agent 有机会“查资料”，而不是只能依赖初始 prompt。

## 5. MCP 解决的第四件事：工具复用

如果一个工具按统一协议暴露，它就不只服务于一个 agent。

例如一个 `search_blog_articles` server 可以被多个客户端使用：

- 网站问答入口。
- 本地写作助手。
- 后台内容运营工具。
- 代码编辑器里的 agent。

工具提供方只需要维护一套协议实现，客户端按标准接入。

这能降低生态重复建设。

但复用不等于所有客户端都能做同样事情。权限和策略仍然要按客户端、用户和场景控制。

## 6. MCP 不解决权限设计

统一协议不会自动让系统安全。

如果一个 server 暴露了：

```text
delete_production_database
```

即使它用的是标准协议，也仍然危险。

权限必须在工具服务端执行：

- 谁可以调用这个工具？
- 可以访问哪些资源？
- 写操作是否需要确认？
- 是否允许跨租户访问？
- 是否要记录审计日志？

客户端 prompt 里写“不要调用危险工具”是不够的。

MCP 只是连接方式，不是权限模型本身。

## 7. MCP 不解决产品边界

工具暴露出来，不代表产品就应该让用户直接使用。

例如：

```text
read_file
write_file
run_shell_command
deploy_to_production
send_email
```

这些工具非常强，但产品层面要决定：

- 用户是否理解这些动作？
- 出错后怎么回滚？
- UI 里怎么展示确认？
- 是否需要审批流？
- 是否符合组织安全策略？

协议能让工具接上，不能替你决定产品体验。

一个好的 agent 产品，不是把工具列表丢给模型，而是把工具放进合适的任务流程里。

## 8. MCP 不解决工具质量

一个工具即使用标准协议暴露，也可能很难用。

常见问题：

- 描述含糊。
- schema 太宽。
- 返回值太大。
- 错误码不清楚。
- 没有分页。
- 没有幂等。
- 没有版本。
- 权限错误和资源不存在混在一起。

这些问题要靠工具设计解决。

MCP 能让工具被发现和调用，但不能让一个坏工具变成好工具。

## 9. MCP 和 RAG 的关系

RAG 可以通过 MCP 暴露成工具和资源。

例如：

```text
tools:
  search_knowledge_base
  rerank_evidence

resources:
  kb://documents/{id}
  kb://chunks/{id}
```

博客问答入口可以调用：

```text
search_knowledge_base(query="RAG 为什么要重排？")
```

然后读取返回的 chunk 或文章资源。

这样 RAG 不再只是某个后端服务内部逻辑，而可以成为 agent 生态里的可复用能力。

但仍然要记住：

```text
MCP 暴露检索能力
RAG 负责找证据
LLM 负责生成回答
权限和引用校验仍然要独立设计
```

## 10. MCP 和 LLMWiki 的关系

如果你后续使用 LLMWiki，它更像知识层。

LLMWiki 可以负责：

- 把文章整理成模型友好的 Markdown。
- 保留标题、章节、链接、引用。
- 生成知识图谱或主题关系。
- 提供搜索和读取能力。

MCP 可以负责：

- 把这些能力暴露给不同 agent。
- 让 agent 发现可读资源。
- 让工具调用有统一 schema。

关系可以这样理解：

```text
博客内容
  -> LLMWiki 整理成知识层
  -> MCP 暴露搜索/读取工具
  -> Agent 调用工具回答用户
```

LLMWiki 解决“知识如何组织”，MCP 解决“工具如何接入”。

## 11. 一个博客 MCP server 可以暴露什么

如果给当前博客做一个 MCP server，可以从很小的能力开始：

```text
resources:
  blog://series/ai-learning
  blog://articles/{slug}

tools:
  list_ai_learning_series
  search_blog_articles
  read_blog_article_section
```

`list_ai_learning_series` 返回 12 篇主线文章：

```json
{
  "series": "ai-learning",
  "articles": [
    {
      "order": 1,
      "title": "大模型如何生成文本：从 Token 到下一个 Token",
      "slug": "llm-autoregressive-generation"
    }
  ]
}
```

`search_blog_articles` 返回证据块：

```json
{
  "query": "RAG 为什么要重排",
  "results": [
    {
      "citationId": "1",
      "title": "RAG 进阶：混合检索、重排、GraphRAG 和评测集",
      "url": "/blog/rag-advanced-hybrid-rerank-graphrag-evaluation",
      "snippet": "候选召回的目标是别漏掉答案，重排的目标是把最能回答问题的证据放前面。"
    }
  ]
}
```

这样 agent 不需要知道博客内部是 Astro、Notion、MDX 还是 PostgreSQL。

## 12. MCP server 的边界

一个 MCP server 不应该什么都做。

建议边界清晰：

```text
blog mcp server
  -> 文章搜索
  -> 文章读取
  -> 系列列表

postgres mcp server
  -> schema 读取
  -> 只读查询
  -> 受控写操作

deployment mcp server
  -> 查看部署状态
  -> 触发部署
  -> 回滚部署
```

不要做一个万能 server，把所有工具堆在一起。

边界越清楚，权限越容易控制，模型也越容易选对工具。

## 13. 工具协议不能替代评测

工具接入后，还要评测 agent 是否真的用对。

可以测试：

- 用户问博客内容时，是否调用博客搜索工具？
- 需要读取原文时，是否调用 read 工具？
- 无权限资源是否被拒绝？
- 写操作是否停在确认点？
- 工具失败时是否正确恢复？

统一协议解决“能调用”，评测解决“调用得对不对”。

没有评测，工具越多，问题越隐蔽。

## 14. 小结

MCP 这类统一协议的价值在于工具生态：

- 统一能力发现。
- 统一工具 schema。
- 统一资源读取。
- 降低客户端和工具的耦合。
- 让能力可以复用。

但它不解决：

- 权限边界。
- 产品流程。
- 工具质量。
- 错误恢复。
- 人类确认点。
- RAG 评测。
- Agent 行为评测。

所以更准确的理解是：

```text
MCP 是工具生态的连接层，不是 agent 系统的全部。
```

## 14.1 面试时怎样把原理讲完整

可以先用下面这段回答建立主线，再按追问展开具体版本与报文：

> MCP 是模型应用连接外部工具和数据的标准协议。应用作为 Host，通过内部的 MCP Client 连接 Server，发现工具描述和参数 Schema。模型生成调用意图后，Host 检查策略并分派，由 Client 发送协议请求，Server 执行后返回结果；Host 再把结果加入模型上下文，让模型继续。底层采用 JSON-RPC 2.0，常见传输是本地 stdio 和远程 Streamable HTTP。版本发现、工具通信、模型推理和实际业务权限有各自的责任。

面试里的几个比较问题，重点在边界：

| 追问 | 回答重点 |
| --- | --- |
| MCP 与 Function Calling 有什么区别？ | Function Calling 是模型表达结构化调用的接口机制；MCP 统一应用与工具服务之间的发现和调用，Host 可以把 MCP 工具映射给模型使用。 |
| 已经有 REST API，为什么还需要 MCP？ | 可以在原 API 上包装 MCP Server，统一工具描述与调用入口；业务接口、认证和数据权限仍需要实现。 |
| 接入 MCP 是否需要重新训练模型？ | 应用通常动态提供工具定义，使用支持工具调用的模型即可；识别和使用某个工具的质量仍需要评测。 |
| MCP Server 是否一定包含模型？ | 不需要。只查询数据库或搜索文章的服务也可以实现它。 |
| 工具越多，Agent 是否越强？ | 还取决于描述、工具筛选、上下文预算、权限与评测，工具数量不是完成任务的保证。 |

回答之后可以落到博客搜索的例子：讲清用户输入、工具发现、模型决策、协议调用、结果回填和异常处理，比只列概念更能证明理解。本文报文仅用于解释协议结构，没有启动真实 MCP Server 或进行端到端调用测试。
