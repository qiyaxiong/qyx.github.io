## 一句话结论

优质图片分析不是把画面描述得更长，而是建立一条可复查的证据链：模型看到了什么，依据哪些区域建立关系，得出了什么判断，还有哪些内容不能仅凭图片确认。

最实用的原则是：

```text
可观察事实 ≠ 关系判断 ≠ 解释性推断 ≠ 已验证结论
```

如果输出没有区分这四层，语言越流畅，误导性反而可能越强。

## 为什么“描述图片”不等于分析图片

普通描述经常只做物体清单：“图里有一个人、一台电脑、一张表格。”它没有回答用户真正关心的问题，也没有说明这些对象之间的关系。

另一种失败是过度解释。模型看到一张仪表盘截图，就直接断言业务下滑；看到人物表情，就判断其心理状态；看到商品照片，就承诺材质和真伪。这些结论已经超出像素能支持的范围。

真正的分析必须同时处理三种约束：

- 任务约束：用户究竟要找错误、读数据、比较差异，还是做设计评价？
- 证据约束：原图中哪些像素、文字、布局或相互关系支持结论？
- 认识约束：哪些信息模糊、缺失，哪些结论需要外部资料或人工验证？

因此，第一步不是“让模型自由看看”，而是定义分析任务和结论的证据门槛。

## 四层证据模型

### 第一层：可观察事实

只记录图片直接呈现的内容，不解释原因。例如：

- 页面右上角出现红色错误提示；
- 折线在 14:00 后明显下降；
- 商品包装上可辨认出 `500 ml`；
- 文档第二段有一处黄色高亮。

事实应该尽量带位置、数量、颜色、方向和可读文字。与其写“界面有问题”，不如写“提交按钮下方出现红色提示，文字为 Network Error”。

### 第二层：关系与结构

在事实之上识别空间、顺序和对应关系。例如，图例中的蓝色对应收入曲线；错误提示紧邻表单邮箱字段；两张截图的导航栏宽度不同。

关系判断让图片从对象清单变成结构化信息，也是表格、流程图、UI 和多图比较中最有价值的一层。

### 第三层：解释性推断

推断回答“这可能意味着什么”。例如，曲线骤降可能与统计口径变化有关；按钮不可用可能因为必填项未完成；两张商品图可能来自不同批次。

推断必须使用“可能”“更符合”“需要进一步确认”等表达，并紧跟依据。没有依据的推断只是语言模型补全。

### 第四层：验证与行动

高质量输出还要告诉读者怎样验证：查看原始数据、放大某一区域、补充另一视角、检查网络请求、对照设计规范，或请领域专家复核。

这一步把分析从“看起来有道理”变成可执行的调查。

## 输入准备决定分析上限

### 保留原始分辨率

社交软件压缩、网页缩略图和二次截图会损失小字、刻度与边缘细节。分析图表、票据或 UI 时，优先提供原图，而不是把多张图片拼成一张低清长图。

### 原图与局部裁剪同时提供

原图负责上下文，裁剪图负责细节。只给裁剪图，模型可能不知道元素属于哪个页面；只给原图，小区域又可能无法辨认。

推荐的输入组合是：

```text
图片 A：完整画面，用于理解全局结构
图片 B：目标区域裁剪，用于读取细节
图片 C：对照图或另一视角，用于验证判断
```

### 明确图片顺序和角色

多图任务应标注“修改前”“修改后”“正面”“背面”“移动端”“桌面端”。如果顺序本身有意义，不要让模型猜测。

### 补充最少但必要的上下文

同一张图在不同任务中结论完全不同。看到网站截图时，设计师关心层级，测试工程师关心异常状态，安全人员关心敏感信息暴露。

有效上下文通常包括：图片来源、拍摄或截图条件、分析目标、允许使用的外部知识，以及答案将被用于什么决策。

## 把 Prompt 写成任务契约

一个稳定的图片分析请求，至少应包含四个字段。

### 1. 目标

不要只说“分析这张图”，要明确期望决策。例如：

- 找出移动端布局中影响阅读的三个主要问题；
- 读取图表的趋势，但不要推断未展示的数据；
- 比较 A、B 两图的可见差异；
- 检查合同截图中日期和金额是否一致。

### 2. 证据范围

说明模型可以使用什么：仅依据图片，还是可以结合附带文档、网页资料或领域常识。需要联网核验时，应把图片观察与外部事实分开呈现。

### 3. 输出结构

固定结构能迫使模型暴露推理边界。推荐字段包括：位置、观察、解释、置信度、验证方法。

### 4. 禁止推断

明确哪些信息不能猜。例如，不根据面部推断敏感属性，不凭包装图片判断真伪，不把图中相关性写成因果关系，不补全看不清的文字。

## 一套可复用的分析流程

### 第一步：建立画面清单

先判断图片类型、主体、区域数量、文字密度和清晰度。此时只做全局定位，不急着下结论。

可以用一句内部检查：

```text
这是什么类型的图？有哪些主要区域？任务目标落在哪些区域？
```

### 第二步：按区域提取证据

把画面划分为顶部、主体、侧栏、底部，或按图表面板、表格行列、文档段落来切分。每条观察都绑定一个位置，避免把不同区域的信息混在一起。

### 第三步：识别对象关系

检查颜色与图例、标签与输入框、标题与正文、箭头与节点、人物与物品之间的对应关系。多图任务还要建立同一对象在不同图片中的配对。

### 第四步：形成有限推断

只对任务相关事实进行解释，并给每个判断附上依据。若存在两个合理解释，应并列呈现，而不是选择语言上最顺畅的一个。

### 第五步：寻找反证和矛盾

主动问：

- 是否有其他区域不支持当前判断？
- 坐标轴是否被截断？
- 图例颜色是否相近到容易混淆？
- 截图是否只展示了异常发生后的状态？
- 两张图的拍摄角度、光线和缩放是否一致？

这一步能够显著减少“看见相关模式就立即讲故事”的问题。

### 第六步：标注置信度与缺口

置信度不是装饰性的百分比，而应对应证据质量。

```text
高：文字或结构清楚，结论可直接由图片复核
中：主要证据可见，但存在遮挡、模糊或另一种解释
低：依赖小字、间接线索、外部背景或不完整画面
```

如果缺口可以通过一张补充图片解决，就明确说出需要拍哪里、截哪一屏，而不是笼统要求“提供更多信息”。

## 不同图片需要不同读法

### UI 与网页截图

先确认页面状态、视口尺寸、交互目标，再检查层级、对齐、间距、可读性和状态反馈。区分视觉偏好与可用性缺陷：颜色“不够好看”是偏好，按钮被遮挡导致无法提交是功能问题。

分析错误截图时，应同时读取错误文字、触发位置和周围状态。如果只有最终画面，不能擅自还原完整操作步骤。

### 图表与数据可视化

依次检查标题、时间范围、坐标轴、单位、基线、图例、数据标签和来源。先读数，再描述趋势，最后才讨论可能原因。

常见陷阱包括截断纵轴、双坐标轴、累计值与增量值混用、不同时间窗口对比，以及把面积或颜色深浅误当成精确数值。

对于无法精确读取的点，应给区间或相对关系，不要制造小数点后的确定性。

### 文档、表格与 OCR

先保持原始结构，再提取内容。合同、发票、试卷和表格里的行列位置本身就是语义，直接输出一长段文本会丢失字段对应关系。

对关键字段采用“原文转写 + 标准化结果”双栏方式。例如先保留图片中的日期写法，再给出统一格式。模糊字符用 `[不清晰]` 标记，不凭上下文偷偷补全。

金额、日期、编号和姓名属于高风险字段，至少进行一次局部放大复核。若结论将用于付款、签约或合规判断，必须保留人工确认。

### 实物、场景与商品图片

区分外观观察与属性证明。图片可以支持“表面有划痕”“接口形状类似 USB-C”，但通常不能单独证明内部材质、真实性、故障原因或安全等级。

光线、白平衡、透视和镜面反射都会改变颜色与尺寸感知。需要比较时，应尽量统一拍摄距离、角度、背景和光源。

### 多图比较

先固定比较维度，再逐项对齐。可用维度包括：对象是否存在、位置、尺寸、颜色、文字、状态和时间。

只有 A 图有、B 图没有的内容，应先判断是否因为裁剪或视角不同。像素差异并不自动等于对象发生了变化。

## 推荐的结构化输出

复杂任务可以要求模型使用下表：

| 位置          | 可观察事实               | 解释或影响               | 置信度 | 如何验证                 |
| ------------- | ------------------------ | ------------------------ | ------ | ------------------------ |
| 右上角        | 出现红色 `Network Error` | 请求可能失败，但原因未知 | 高     | 查看浏览器 Network 面板  |
| 主图 14:00 后 | 蓝色曲线快速下降         | 指标在该时段降低         | 高     | 对照原始数据与指标定义   |
| 底部按钮      | 颜色变灰                 | 可能处于禁用状态         | 中     | 尝试完成必填项并观察状态 |

简单任务也可以使用四段式：

```text
结论：
关键证据：
不确定项：
下一步验证：
```

输出结构的价值不是让答案更像报告，而是把事实、推断和行动分开，使错误更容易被发现。

## 质量检查表

提交结果前，可以用八个问题做快速复核：

1. 是否直接回答了用户的真实任务？
2. 每个关键结论能否指回具体图片区域？
3. 是否把可见事实和解释性推断分开？
4. 是否保留了单位、时间、图例与上下文？
5. 看不清的内容是否明确标注，而不是补全？
6. 是否考虑了裁剪、压缩、光线和视角造成的偏差？
7. 高风险字段或结论是否给出验证方法？
8. 输出是否足够短，让读者能够快速复核？

其中任何一项失败，都应先修正证据链，而不是继续增加描述。

## 常见失败模式

### 把识别结果写成事实数据库

模型可能识别出品牌、地点或人物，但相似外观并不能构成身份确认。应写成“外观与……相似”，并说明需要什么额外证据。

### 用领域常识覆盖图片证据

领域知识适合解释观察，不应替代观察。如果图中坐标轴看不清，就不能因为某类业务通常如此而补出趋势。

### 只报结论，不报位置

“布局混乱”无法复核；“标题、筛选器和首张卡片在 390px 视口内同时争夺首屏，主要操作被推到首屏之外”才是可操作分析。

### 对所有结论给相同置信度

OCR 小字、明显颜色和因果解释的证据强度不同。统一写“我很确定”，只会隐藏风险。

### 输出过长但没有优先级

图片里总能发现许多细节，但用户通常只需要影响决策的少数问题。先给关键结论，再给证据和次要观察。

## 人机协作与验证边界

多模态模型适合做第一轮筛查、结构化提取、差异定位和验证清单生成。它不应成为高风险决定的唯一签字者。

医疗影像、法律文件、支付信息、安全事故和身份判断需要专业流程。模型可以帮助定位疑点，但最终结论应由具备责任与权限的人确认。

工程系统还应保存原图版本、提示词、模型版本、结构化结果和人工修订。没有审计链，就难以解释某个判断为何产生，也无法持续评估质量。

## 可直接复用的 Prompt

```text
你是一名证据优先的图片分析员。

任务目标：
[说明要解决的问题，以及答案将用于什么决策]

输入说明：
- 图片 A：[完整图/修改前/正面等]
- 图片 B：[局部图/修改后/背面等]
- 可使用的背景资料：[列出；没有则写“仅依据图片”]

请按以下步骤分析：
1. 先识别与任务相关的区域，不急于解释。
2. 对每条关键观察标注位置，并转写可辨认文字。
3. 分开写“可观察事实”和“解释性推断”。
4. 为推断给出依据、置信度和可能的替代解释。
5. 列出图片无法确认的信息，以及最小验证动作。

输出格式：
- 结论摘要
- 证据表：位置 / 观察 / 解释 / 置信度
- 不确定项与反证
- 下一步验证

禁止：
- 补全看不清的文字或数字
- 把相关性写成因果关系
- 根据外观推断敏感属性
- 在没有图片证据时使用确定语气
```
