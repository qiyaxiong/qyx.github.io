## 先从问题出发

本节不从类图开始，而从 **游戏地图瓦片** 的变化压力开始：地图每个格子都创建完整纹理与碰撞配置。真正要回答的问题是：怎样证明对象共享真的节省内存，而不是凭感觉增加复杂度？

设计的目标不是消灭修改，而是让一次需求变化只触碰与它同方向的代码。下面这张图把本节决策压缩为“症状—动作—结果”三步。

## 核心判断

**享元工厂** 在这里不是一条必须服从的口号。它是在提醒我们：享元工厂按稳定键缓存不可变 TileType，坐标留给 Tile。其余关键词——缓存键、不可变共享、性能测量——都服务于同一个目的：找到一个调用方能理解、实现方能独立变化的边界。

重构之后期待的不是“类更多了”，而是一个可以验证的结果：纹理和规则只保存一次，实例只保留外部状态。如果做完重构仍然需要在五个文件里同步修改同一种规则，说明边界很可能放错了。

## 最小代码例子

下面的代码刻意只保留决定性的协作关系。真实项目还要补上输入校验、错误模型、日志和测试，但这些不应掩盖本节的依赖方向。

```ts
class TileTypeFactory {
  private cache = new Map<string, TileType>()
  get(key: string, create: () => TileType) {
    if (!this.cache.has(key)) this.cache.set(key, Object.freeze(create()))
    return this.cache.get(key)!
  }
}

const tile = { x: 12, y: 8, type: factory.get('forest', loadForest) }
```

阅读时不要只数接口和类，依次检查：

1. 谁拥有业务决策；
2. 哪个方向会经常变化；
3. 调用方依赖的是业务语言还是供应商语言；
4. 新增一种实现时，稳定流程是否仍要修改。

## 设计前后对照

| 观察点 | 重构前 | 重构后 |
| --- | --- | --- |
| 变化位置 | 地图每个格子都创建完整纹理与碰撞配置 | 享元工厂按稳定键缓存不可变 TileType，坐标留给 Tile |
| 依赖方向 | 稳定逻辑了解易变细节 | 稳定逻辑只依赖明确边界 |
| 验证方式 | 依赖整套环境做回归 | 可以替换协作者并做局部测试 |
| 新增成本 | 修改旧分支并承担连锁风险 | 在边界后新增实现并运行契约测试 |

表格并不保证右侧永远更好。如果变化频率低、实现只有一个且结构非常稳定，多一层抽象可能只是让跳转路径变长。

## 什么时候值得使用

- 已经观察到同一类修改反复发生，而不是只猜测未来；
- 稳定规则与易变实现有清楚的语言边界；
- 可以通过单元测试或契约测试证明替换后的行为；
- 新结构让调用方更接近业务意图，而不是更接近框架术语。

## 什么时候先不要用

本节方案的主要代价是：先用内存剖析验证收益，低基数对象不值得引入缓存。如果团队还说不清变化轴，先保留简单实现、收集第二个真实用例，通常比立即建立通用框架更安全。

另一个检查方法是看删除成本：如果抽象失败，能否在一次小重构中回到直接实现？越难撤销的设计，越需要真实证据。

## 本节小结

享元工厂按稳定键缓存不可变 TileType，坐标留给 Tile。当你能用“变化原因”和“行为契约”解释这个决定时，享元工厂 才从名词变成了可迁移的编程思想。
